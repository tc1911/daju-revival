# 代码文档

本文件覆盖仓库内全部可执行代码：`tools/` 下 21 个源码文件 + `tools/pipeline.toml`，共 2,978 行。
不包含 APK/PNG/MP3 等二进制内容；资源事实见 `docs/原版代码分析.md`。
整份游戏 JS（264 个模块）的逐模块说明见 `docs/游戏代码文档.md`。
目标是把「每个文件做什么、每一段代码改了什么、引用了谁」讲清楚，做到可以只读本文 + 原始脚本复原整条链。

> 行号是 6.12 原版/当前脚本的快照；换底包或大改脚本后以**锚点字符串**为准，行号会漂移。
> 本文只管 tools 与补丁实现；当前产物/验证见 `docs/修改列表.md`，游戏模块见 `docs/游戏代码文档.md`。

**行号约定**

- 全部按 `\n` 分行，与 `grep -n` / `sed -n` 的行号一致。
- 每个补丁章节都标注「输入阶段文件」；例如 `local_account_patch.py` 的行号是
  `work/tmp/project.offline.js` 的行号，不是原始 `project.js` 的行号。
- 插入点在表中写成 `in a-b`（`a=b+1`）表示「在第 a 行之前插入」。

**本文的验证方式**

- 把 10 个 JS 补丁按顺序重放到 `/tmp`，与原阶段产物逐字节比较：全部一致。
- `ProfileBridge.java` 重新 `javac + d8`，与 `classes3.dex` 逐字节一致。
- `daily_currency_assets.py` 重新生成 overlay，与 `work/build/official-arm64-daily` 的 5 个 JSON 逐字节一致。
- 最终 `repack` 重打一遍，APK SHA256 与现有产物一致。
- 3 个 shell 脚本 `bash -n` 全部通过；Python 编译检查发现 1 个 `SyntaxWarning`（见 9.5）。

## 2. 基础工具（逐文件）

### 2.1 `tools/jsc.py`（141 行）

**作用**：`.jsc` ↔ JS。格式为 XXTEA（含长度字）→ gzip。

- 1-8：模块 docstring，写明格式
- 11-16：`argparse/gzip/os/struct/sys/pathlib.Path`
- 18-20：`DELTA=0x9E3779B9`、`MASK=0xFFFFFFFF`、`DEFAULT_KEY=os.environ.get("JSC_KEY","")`
- 23-28 `_key_words()`：空 key 直接退出并提示；key 补零/截断到 16 字节，按小端解成 4 个 `uint32`
- 30-33 `_mx()`：XXTEA 的 MX 轮函数
- 35-54 `xxtea_decrypt()`：
  - `n=(len+3)//4`，`n<2` 抛「密文太短」
  - `sum=(6+52//n)*DELTA`，反序解密
  - 长度字校验 `n*4-7 <= length <= n*4-4`，失败抛「密钥不对？」
  - 返回 `bytes[:length]`
- 57-76 `xxtea_encrypt()`：把长度字追加到 `v` 末尾，正向加密
- 79-82 `decrypt_file()`：XXTEA 解密后，若以 `1f 8b` 开头再 `gzip.decompress`
- 85-89 `encrypt_file()`：默认 `gzip.compress(..., mtime=0)`，再 XXTEA；`mtime=0` 保证可复现
- 92-139 `main()`：
  - `decrypt src dst`
  - `encrypt src dst [--no-gzip]`
  - `decrypt-all src dst`：递归所有 `*.jsc`，输出镜像目录、后缀改 `.js`
  - `selftest src`：只验证 **XXTEA 解密→加密** 是否回原字节，不做 gunzip；对 gzip payload 也成立
- `-k/--key` 或 `JSC_KEY` 环境变量提供 key；构建入口不传 `-k`，依赖环境变量

**引用**：`argparse`、`gzip`、`os`、`struct`、`sys`、`pathlib.Path`。

**实测**：`JSC_KEY=... jsc.py selftest project.jsc` → `339332 -> 339327 B, 重新加密一致 = True`。

### 2.2 `tools/unpack_apk.sh`（19 行）

- 1-3：用法注释
- 4：`set -euo pipefail`
- 6-9：取 `APK/OUT/KEY`；`KEY="${JSC_KEY:?请先 export JSC_KEY=...}"`
- 11-13：`unzip -o -q "$APK" -d "$OUT"`
- 15-19：若存在 `assets/src`，调用
  `python3 jsc.py -k "$KEY" decrypt-all "$OUT/assets/src" "$OUT/assets/src-js"`；
  否则打印警告并跳过

**注意**：解密结果落在 `assets/src-js/`（带 `-js`），不是 `assets/src/`。

### 2.3 `tools/repack_zip.py`（71 行）

**作用**：把 overlay 覆盖进 APK，其余条目原样搬运，并删掉旧 v1 签名。

- 16：`SIGN_SUFFIXES=(".SF",".RSA",".DSA",".MF",".EC")`
- 19-20 `is_old_signature()`：`META-INF/` 且以签名后缀结尾
- 23-57 `repack()`：
  - 24-28：overlay 内所有文件 → `relative_path -> Path`
  - 29-31：`replaced` 集合、`copied` 计数
  - 33-50：遍历原 APK 条目
    - 旧签名条目直接 `continue`（丢签名）
    - 同名 overlay 文件 → 读 overlay 内容
    - 否则读原条目
    - 新建 `ZipInfo` 并复制：`date_time`、`compress_type`、`external_attr`、`internal_attr`、`create_system`；清掉 `flag_bits & ~0x08`（data descriptor）
    - `writestr`
  - 51-56：overlay 里新增的条目（原 APK 没有）按路径排序后写入
    - `ZipInfo(name)` 默认时间 1980-01-01、默认 `ZIP_STORED`（不压缩）
    - 这就是 `classes3.dex` 在 APK 里是 store、且时间为 1980 的原因
  - 57：返回 `(copied, replaced_count)`
- 60-67 `main()`：参数必须 3 个，打印 `条目 N 条（覆盖/新增 M 条）`

**实测 APK 条目**：`classes.dex/classes2.dex` 是 deflate；`classes3.dex` 是 store；
`assets/src/project.jsc` 是 store（因为原 APK 里就是 store）；`assets/main.js` 是 deflate。

### 2.4 `tools/repack_apk.sh`（51 行）

**作用**：覆盖 → 对齐 → 签名 → 校验。

- 1-7：用法注释；要求 `KS`、`KS_PASS`、可选 `KS_ALIAS`
- 10-14：`APK/OVERLAY/OUT/HERE/ROOT`
- 16-20：`TMP=work/tmp`、`KS=${KS:-work/keystore/daju.jks}`、`KS_ALIAS=${KS_ALIAS:-daju}`、`KS_PASS`（必填）
- 22：创建 TMP、输出目录
- 24-30：keystore 不存在时直接报错，并提示用 `keytool` 自行生成；**不再自动生成密钥、不写死密码**
- 32-34：中间产物按输出 basename 命名：
  `work/tmp/<base>.unsigned.apk`、`work/tmp/<base>.aligned.apk`
- 37：`python3 repack_zip.py`
- 40：`zipalign -f -p 4`
- 43-46：`apksigner sign --v1-signing-enabled true --v2-signing-enabled true`（v3 默认开）
- 48-51：`apksigner verify --verbose --print-certs | head -20`，打印成品大小

**注意**：`head -20` 会截掉部分 WARNING；验证签名以 `apksigner verify --print-certs` 单独跑为准。

### 2.5 `tools/merge_official_arm64.sh`（83 行）

**作用**：官方底包 + compat/OPPO 的 arm64 `.so`。

- 1-12：用法注释；`ROOT`、默认官方/OPPO/输出、overlay
- 14-16：`COMPAT_DIR=${COMPAT_DIR:-compat/arm64-v8a}`、`COMPAT_LIST=${COMPAT_LIST:-compat/libs.txt}`
- 18-19：官方 APK 检查；取官方 `lib/armeabi-v7a/*.so` 的 basename 集合
- 21-31：compat 优先：
  - 逐行读 `compat/libs.txt`，跳过空行/注释
  - 每个文件必须存在，否则直接报错
  - 非空则 `compat=1`
- 33-42：compat 不完整时回退：
  - 要求 OPPO APK 存在
  - OPPO `lib/arm64-v8a/*.so` 与官方 v7a 取交集
- 44-60：重建 overlay；compat 模式 `cp`，回退模式 `unzip -p`，逐个打印大小
- 62-73：`comm -23` 找官方 v7a 有、arm64 侧没有的库，打 WARNING

**数据**

- 官方 v7a：8 个（`lib39285EFA`、`libbreakpad-hei`、`libbuffer_pg`、`libcocos2djs`、
  `libfile_lock_pg`、`libnms`、`libtobEmbedEncrypt`、`libsgcore`）。

- OPPO arm64：9 个（多 `libads-c`、`libnearmelog`）。
- `libads-c` / `libnearmelog` 是 OPPO 渠道 SDK，不进入 compat，也不合并。

**实测**：`compat` 模式与旧 OPPO 提取模式产出的 merged APK SHA256 相同，
最终 `official-arm64-local-nopay.apk` 也仍然是
`469272483d102282d787e53973f1c8e3da960d3613a13c03ca3d634792f81b7f`。

## 3. JS 补丁逐项

JS 补丁共 10 个阶段，按 1.2 的顺序执行。所有阶段都通过

### 3.1 `tools/offline_skip_launcher.py`（59 行）

**输入/输出**：`project.js` → `project.offline.js`（+1 行）
**导入**：`sys`

**代码结构**

- 29-37 `NEW_HOT`：在 `t.loadingLabel.active` 前插入：
  `cc.default.clientAssetsVersion="6.12"`、`hotUpdateStatus=1`、日志、`return`
- 40-55 `main()`：对两段 anchor 各检查 `count==1`，替换，写出

**修改表**（输入 `work/extracted/oppo/assets/src-js/project.js`）

| # | 输入行 | 输出行 | 修改 |
|---|---:|---:|---|
| 1 | 29200-29204 | 29200-29201 | `login_getClientConfig` 请求对象整段替换为 `console.log(...)` + `e.initCb("6.12")` |

**引用/含义**

- `l.default` 是 `HttpRequest`，原请求会等已停服务器超时（约 102 秒）；替换后不再发请求。

### 5.2 `tools/build.py`（469 行）

**CLI**

```bash
tools/build.py list
tools/build.py [stage] [--out PATH] [--dry-run]
tools/build.py --force
tools/build.py stage --no-deps
tools/build.py back --force-native
```

- 启动时 `validate_table()` 校验 stage id、base、patch/asset/native 引用；表写错立即报错
- 无参数：构建 `default_stage`（`profile-native`）
- `--out`：只覆盖最终 APK，不改进程中的中间产物
- `--force`：从 merge 起重跑整条依赖链
- `--no-deps`：不重跑上游；缺 base APK/JS 直接报错
- `--dry-run`：只打印命令，不删 overlay、不落盘
- `--keep-overlay`：保留 overlay 旧文件（默认整目录重建）
- `--force-native`：删掉 `work/tmp/official_back_full` 后重新 apktool 解包

**依赖解析**

1. `base = "merged"`：先 merge；`--no-deps` 且 merged 已存在则跳过
2. `base = <stage>`：base APK 不存在、需要 JS 但 base JS 不存在、`rebuild_base` 或 `--force` 时递归构建上游
3. 用 base stage 的最后一个 patch 输出作为 JS 输入；`merged` 用原始 `project.js`
4. 顺序执行 `patches`，每步输入是上一步输出
5. 重建 overlay，把最终 JS 加密成 `assets/src/project.jsc`
6. 可选：`assets` 写资源；`main_js` 写 `assets/main.js`
7. 可选：`native.back` 生成并解出 `classes.dex/classes2.dex`；`dex.profile_bridge` 生成 `classes3.dex`
8. `repack_apk.sh` 以 base APK + overlay 打包签名

**原生步骤**

- `native.back`：
  - `apktool d -f -p work/tmp/apktool_framework -o work/tmp/official_back_full 官方包`
  - `AndroidBackBridge.smali` 不存在时跑 `back_smali_patch.py`
  - `apktool b` 后从产物里抽 `classes.dex`、`classes2.dex` 放进 overlay
- `native.profile_bridge`：
  - `javac -source 8 -target 8` 编 `ProfileBridge.java`
  - `jar cf` 打包，优先 Java 11 + `d8.jar`，否则 PATH 的 `d8`
  - `classes.dex` 复制为 overlay 的 `classes3.dex`

**等价性验证**

- 2026-10-18 用 `tools/build.py profile-native --force` 从 merge 起重建整链，
  最终 APK SHA256 与旧链产物逐字节一致：
  `5190e8e3f92a7494548c5ba2dbb3c366c06d5da5021a481b41526ad1730ab219`
- 单独重跑 `back`、`daily`、`profile` 也分别与对应旧 APK 同 SHA256/同大小
- 因此表驱动迁移没有改变产物，只改变了编排方式

### 5.3 维护规则

- 加补丁：在 `[patches.<id>]` 写 script/out/desc，再把 id 加进目标 stage 的 `patches`
- 加阶段：复制一个 `[[stages]]`，填 `base`、`patches`、`apk_out`
- 改资源/原生步骤：改 `[assets.*]`/`[native.*]`，不要在 `build.py` 里写死
- 只有新增「步骤类型」才改 `build.py`；普通补丁/阶段调整只改表
- overlay 默认 `work/build/official-arm64-<id>`；旧 `-js` 目录可删

## 9. 已知陷阱与不一致

### 9.1 顺序依赖

- `settings_cleanup_patch.py` 的 `REFRESH_OLD` 是 `custom_profile_patch.py`
  插入的 3 行；单独跑 settings 会失败。
- `daily` 读 `project.back.js`，`shop` 读 `project.daily.js`，
  `profile` 读 `project.shop.js`，`profile-native` 只读 `profile.apk`；
  只改下游时从对应 stage 开始，但上游补丁不会自动重跑。
- 改 offline/local/monetization/album/back 后，必须重跑上游：
  `tools/build.py profile-native --force`（整链）或 `tools/build.py back`
  （会自动重跑 nopay 与 merge）；只改下游时用 `--no-deps` 并确保 base 是最新的。

### 9.2 边界锚点的脆弱点

- `remove_monetization` 用 `showTimeLimitPack(e, t)` 和
  `showTimeLimitPack(e, t, n)` 两个重载作为 `addMoodLayer` / `popLogin` 的右边界；
  如果原版方法顺序/签名变化，截断会错。
- `album_perf_patch` 依赖 `AlbumUI: [` 后第一个 `refreshView` 和 `onClose`。
- `custom_profile_patch` 依赖 `GameSetting: [` 后第一个 `refreshView`、
  `setOwnInfo` 到 `freeRecharge`、`getUid` 到 `getRmb`。
- `chat_image_fallback_patch` 依赖 `ImageView: [` 后第一个
  `t.prototype.show(e,t)` 和 `doubleClick`；`patch_caller` 用
  `chunk.replace(...)` 替换该 chunk 内**所有** `showBigImage(t)`，当前正好 2 处；
  如果原版新增调用点会被一起改。
- `repack_zip.py` 只按相对路径匹配；overlay 层级放错会静默变成新增文件。

### 9.3 行为残留

- `FULL_POWER_JS` 每 100ms 递归遍历场景并重绘；`BATT_NEW` 还有一套 60 秒
  组件级 HUD。两套逻辑并存，最终视觉以场景级 HUD 为主。
- `PERSIST_JS` 仍在文件里但未启用；不要误开启，否则会和 `UserDefault` 真实持久化打架。
- `custom_profile_patch` 的 `BAG_ANCHOR` / `CLICK_ANCHOR` 是死代码。
- `getUid` 被替换成「打开资料编辑」，原版点 UID 复制数字的功能消失。
- `main.js` 原热更引导代码未删除，只是启动前清空缓存；要彻底摘除需另改。
- `remove_monetization` 只删 `FeedBack_1`（问卷），`FeedBack`（客服）仍保留。

### 9.4 构建/打包

- `repack_zip.py` 对新增条目使用默认 `ZipInfo`：1980-01-01、ZIP_STORED；
  现有条目保留原压缩方式。`project.jsc` 在原 APK 里是 store，所以最终也是 store。
- `repack_apk.sh` 中间产物按输出文件名命名；同名并发构建会互相覆盖。
- `native.back` 的 `official_back_full` 是缓存：
  存在且已有 bridge 时不会重新解包/打 smali；smali 改动后用
  `tools/build.py back --force-native`。
- `compat/arm64-v8a/` 缺少 `libsgcore.so` 的 arm64 版本；当前能启动，但涉及该库的功能未验证。
- `compat/` 不包含 OPPO 渠道库 `libads-c.so` / `libnearmelog.so`。
- `[native.profile_bridge]` 缺 `android.jar` 时会联网下载；离线环境需预先放好。
- `d8` 必须 Java 11；`javac` 用默认 Java 8。
- `daily_currency_assets.py` 的 glob 是硬编码相对路径，必须在仓库根目录执行。
- stage 的 `base` 和产物都写在 `tools/pipeline.toml`；换底包/换输出改表，
  不要改 `build.py`。

### 9.5 已知代码质量问题

- `chat_image_fallback_patch.py:62` 的 `\.png` 是 Python 非法转义，当前只告警。
  修法是改成 `\\.png` 或 raw string；未改代码，避免影响已复现的 stage 产物。
- `offline_skip_launcher.py` 的 `NEW_LOGIN` 把原请求对象整个删掉，
  只保留 `e.initCb("6.12")`；如果以后需要 `pf/gid/versionName`，要重新补。
- `local_account_patch.py` 的 `getUser` 回调字段是手写的，原版新增字段不会自动补。
- `ProfileBridge.java` 有 4 个未使用 import；不影响编译。
- `ProfileBridge` 用反射拿 `Cocos2dxHelper` / `Cocos2dxJavascriptJavaBridge`，
  类名或方法签名变化会静默失败（catch Throwable）。

## 10. 维护清单

改任何补丁后按这个顺序检查：

1. **只改一个阶段**：在该阶段输入 JS 上跑 patch，和已有输出 `cmp`。
2. **改上游**：`tools/build.py profile-native --force` 重跑整链；
   或 `tools/build.py back` 只重跑 back 及其上游。
3. **改 JS 锚点**：先 `grep -n` 确认 anchor 在输入文件里恰好出现 1 次；
   边界方法用 `find(start)`/`find(end)`，确认 `end > start`。
4. **改原生/资源**：重跑 `ProfileBridge` 的 javac+d8 或
   `daily_currency_assets.py`，与现有 overlay `cmp`。
5. **重打包**：`repack_apk.sh` 后跑
   `apksigner verify --print-certs`，并解密 APK 内 `project.jsc` 与
   `work/tmp/project.final.js` 对比。
6. **清缓存**：只删 `work/tmp` 里的截图/日志/中间 `.apk`；
   `project.*.js`、`main_nohot.js`、`native_profile/android.jar`、
   `official_back_full/`、`apktool_framework/` 不要删。
7. **改文档**：如果行号/锚点变了，同步更新本文件对应章节；
   不要只改代码不改文档。
